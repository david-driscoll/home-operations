# 07 — Authentik moves to alpha-site (G′)

Planning piece for [vault#84](https://github.com/david-driscoll/vault/issues/84). Part of the
[cluster consolidation plan](README.md). Decision **D4** (Q-C): *"With the USB SSD it should be
fine"* — David accepted moving the estate's SSO off Kubernetes entirely, onto the Pi.

This is the largest single piece in the plan outside the node phases themselves. It removes
Kubernetes — and therefore the SGC→equestria merge — from authentik's blast radius before any
node is touched. Everything in this file can be executed and verified independently of every
other piece except **[03 — secrets bootstrap independence](03-secrets-bootstrap-independence.md)**,
which is a hard prerequisite (§3.4 below).

## Scope

Move authentik's **server and worker** processes, its **PostgreSQL database**, and a bundled
**Redis**, off equestria/SGC Kubernetes and onto alpha-site as Docker containers under Dockge.
Embedded and proxy **outposts stay in-cluster**, next to the apps they front — only the central
server relocates. Traefik's `forwardAuth` target repoints at alpha-site. The SGC copy is dumped,
restored, verified, cut over, soaked, then scaled to zero (never deleted, until
[22 — decommission SGC](22-decommission-sgc.md)).

This piece does **not** touch: outpost creation/registration mechanics (already cross-cluster,
§1.5), the `stacks/authentik` Pulumi stack that manages authentik's *objects* (flows/groups/
providers — unaffected, it only needs a reachable API endpoint), or any app's own OIDC client
config (unaffected — the issuer URL doesn't change, only what answers behind it).

**What this means for concentration risk:** the July discovery (v2.1 §2.1, 2026-07-30) argued
alpha-site would hold "identity, netboot.xyz, Gatus, AdGuard, Z-Wave, neo4j, Prometheus" and
called that the binding objection to adding anything further. **`bao-transit` and `bao-standby`
did not exist yet when that was written** — they landed as part of the OpenBao migration that
completed 2026-08-12 (see the repo root `CLAUDE.md` memory index / `vault` repo
`docs/openbao-migration/STATUS.md`). Today's list is strictly worse: alpha-site is now the
**sole unseal path** for equestria's secret store *and* the proposed home for the estate's SSO.
Neither fact is a reason to reverse D4 — David already weighed durability against the USB SSD
(§1.2) — but it sharpens the rule this piece must state plainly: **once authentik lands here,
nothing else new goes on this Pi**, full stop, not "until the next hardware refresh."

|---|---|

| `sda` I/O, 24 h avg | 8.9 write IOPS, 173 KB/s, 0.69% busy |
| `sda` write latency, 24 h avg | **1.40 ms** (~3.3× luna's NVMe at similar load) |
| `sda` write latency, peak 5-min/7d | 3.25 ms at 9× the average IOPS, only 22% busy |

| SD card (`mmcblk0`) I/O, 24h | **zero** — confirmed out of the data path entirely |

The `mmcblk0`-vs-`sda` question that killed the July v2 recommendation is closed: everything on
alpha-site already lives on the USB SSD, which is what changed David's answer between v2 (Q-C
recommended keeping authentik in-cluster) and his reply (*"with the USB SSD it should be
fine"*), formalized in v2.1.

**What is not measured, and is the one real unknown:** `node_disk_write_time_seconds_total`
covers request service time, not `REQ_OP_FLUSH` specifically. USB-SATA/NVMe bridges are known to
either serialize `fsync` slowly or silently ignore FUA — the second is data loss on a power cut,
not a latency number. This is §3.1's hard prerequisite, not optional due diligence.

### 1.5 The outpost-split precedent already exists and is already cross-cluster

Two facts make "outposts stay in-cluster, server moves" a *smaller* architectural change than it
sounds:

1. **`docker/_common/authentik-outpost`** is a real, already-deployed component (`.env` +
   `compose.yaml`) — any Dockge host can run a proxy outpost that dials *out* to a remote
   authentik server. `components/DockgeLxc.ts:708-734` (`deployStacks`'s `outpost` block) creates
   one automatically per Dockge host whenever any deployed app declares a proxy provider, and
   `components/DockgeLxc.ts:794` (`createOutpost`) is the exact line that writes the outpost's API
   token to `/opt/stacks/authentik-outpost/.env-token` on the remote host over SSH. This already
   runs today, pointed at SGC, on every Dockge host that needs it (celestia's forgejo, for one).
   Nothing about this mechanism needs to change — only where `CLUSTER_AUTHENTIK_DOMAIN` resolves.
2. **Cross-cluster embedded outposts already work.** Both `stargate-command-cluster`
   (`kubernetes/apps/sgc/idp/authentik-remote-cluster/`) and `equestria-cluster`
   (`kubernetes/apps/equestria/idp/authentik-remote-cluster/`) deploy the official
   `authentik-remote-cluster` chart (v2.1.0). Equestria's apps are *already* using
   embedded/proxy outposts against an authentik server that lives in a different cluster,
   over the tailnet. Moving the server from "a pod in SGC" to "a container on alpha-site" is
   the same shape of cross-cluster reach authentik already does today, from a different host.

### 2.1 Why reuse the shared Postgres instead of a dedicated container

v2.1 (2026-07-30) specified a dedicated Postgres container because the generic shared-Postgres
pattern (`docker/_common/postgres`) didn't exist yet on alpha-site. It exists now (§1.1,
commit `2b99cb93`, "Updating postgres deployment"), on every Dockge host, with:

- A provisioner (`postgres-provision`) that reconciles any `PGAPP_<NAME>_PASSWORD` in `.env-local`
  into a login role + owned database, idempotently, on every stack start
  (`docker/_common/postgres/compose.yaml`).
- A `postgres-backup` service that runs `pg_dump` into `/opt/stacks-data/postgres/dumps` on a
  schedule.
- **`stacks/backups/index.ts` already backs this up for every Dockge host generically** —
  `dockgeDetails.apply` iterates every registered Dockge instance (including alpha-site) and
  creates a backrest plan that rclone-pulls `/opt/stacks-data/` (excluding the live `pgdata`
  directory, explicitly, with the exact reasoning about torn vs. crash-consistent copies) and
  restic-snapshots it to celestia, which PBS then covers. **This means the `pg_dump` →
  backrest → PBS chain for authentik's new database is already-existing generic infrastructure,
  not new Pulumi code**, as soon as authentik's Postgres role/database is declared through the
  shared instance. §3.2 still requires proving the *restore* half of that chain, which is not
  automatic.

Using the shared instance instead of a dedicated container also means one less Postgres process
consuming alpha-site's thin headroom (§2.2) and one less thing to independently fsync-test,
back up, and monitor.

### 2.2 Footprint

Measured (from live SGC pods, v2.1 §2.2, reproduced in §1.3's table): server + worker ≈
1.4 GiB across two replicas today; a single-replica Docker deployment (server ×1, worker ×1,
shared Postgres marginal cost for one more small database, bundled Redis) lands at **~2.5–3.0 GiB
steady, well under 1 core**, against the 4.55 GiB available / 3.5 idle cores measured in §1.2.
That leaves roughly **1.5–2 GiB of headroom** — thin enough, especially with `bao-transit` and
`bao-standby` added since that estimate was made (§1.1), that this piece's most important
non-technical output is the rule already stated in §1.1: **nothing else new lands on this Pi.**
Re-measure `node_memory_MemAvailable_bytes` for `cluster="alpha-site"` immediately before
deploying (§3.1) rather than trusting the July number to have held exactly.

## 3. Hard prerequisites — gated, in order

None of these are optional hardening; each is something that must be true, and verified true,
before the corresponding later step runs.

### 3.1 fsync/flush test on `sda`, before Postgres lands (before any of §4 runs)

The one genuine unmeasured risk (§1.2). Run, and record the result in this piece's tracking
issue before proceeding:

```sh
# Either is sufficient; both is better.
pg_test_fsync -f /path/on/sda/testfile
fio --name=fsynctest --rw=write --bs=8k --fsync=1 --size=256m --directory=/path/on/sda

# Correctness signal, not just latency:
hdparm -W /dev/sda            # write-caching enabled?
dmesg | grep -i "usb.*\(uas\|bot\)"   # UAS (queued) vs BOT (bulk-only) bridge mode
```

Gate: fsync latency should be single-digit ms and consistent; if `dmesg` shows the bridge running
BOT rather than UAS, or `hdparm -W` shows write-caching with no way to confirm FUA is honored,
that changes the answer for a database specifically (and does not change the answer for
everything else already running on alpha-site, which doesn't need durable fsync — this is why
the risk was invisible until a database was proposed).

### 3.2 Backup chain proven, including restore, before cutover (before §4 step 3)

- `PGAPP_AUTHENTIK_PASSWORD` provisioned via the shared instance (§2.1) gets the pg_dump →
  backrest → PBS chain for free — but an unverified dump is not a backup. **Restore the alpha-site
  authentik dump into a scratch Postgres and confirm it opens and authentik's schema is intact**
  before this piece is considered done.
- No PITR anywhere applies here regardless of how vault#119 resolves (§1.3) — the alpha-site
  Postgres will not have WAL archiving; the dump/backrest/PBS chain is the only rollback path,
  and rollback granularity is however often the dump runs.

### 3.4 The OpenBao-era break-glass path from piece 03 must exist first

Rebuilding or redeploying authentik on alpha-site is a Pulumi run (`stacks/home` for the Dockge
compose stack, `stacks/authentik` for its flows/groups/providers). Pulumi needs
`PULUMI_CONFIG_PASSPHRASE` and every other secret from OpenBao (`.config/mise.toml`:
`ref+openbao://` throughout, confirmed live). If authentik is broken *and* the tool needed to fix
it needs secrets that are unreachable, the estate is stuck. This is worse, not better, after this
piece lands: today authentik being down doesn't threaten Pulumi's ability to fix anything; once
`bao-transit` and authentik are the same box (§1.1), a bad day on alpha-site threatens both the
seal *and* the identity provider at once. **[Piece 03](03-secrets-bootstrap-independence.md)'s
break-glass path — a local `pulumi` run that survives OpenBao being unreachable — is a hard
prerequisite for this piece, not a nice-to-have.** `bootstrap/RUNBOOK.md` Scenario B (vault repo)
documents the OpenBao-side half of this today; piece 03 is what makes the Pulumi-side half true.

There is a second, newer instance of this same class of dependency worth flagging even though
it's outside this piece's scope to fix: `docs/openbao-migration/STATUS.md` (vault repo) confirms
OpenBao's own human OIDC login (`auth/oidc`) uses Authentik as its identity provider (issuer
`https://authentik.driscoll.tech/application/o/equestria-kube-system-openbao-wolf/`, verified
live). If authentik is down, human OIDC login *to OpenBao* is unavailable too — machine access
via the AppRole `pulumi-env.sh` uses is unaffected, but a human trying to inspect OpenBao
directly during an authentik outage needs OpenBao's own root/recovery path, not the SSO one.
Confirm that path is documented and current before relying on it.

### 3.5 `AUTHENTIK_URL` / `AUTHENTIK_TOKEN` repoint

`.config/mise.toml` (verified):

```
AUTHENTIK_TOKEN = "ref+openbao://secrets/shared/authentik-token#/credential"
AUTHENTIK_URL   = "ref+openbao://secrets/shared/authentik-token#/url"
```

These are Pulumi *provider* inputs for `stacks/authentik`, which manages authentik's objects via
`@pulumi/authentik` — it does not deploy authentik itself. No code change is needed here; the
repoint is a **secret-value update**: after alpha-site's authentik is up and has a fresh API
token, update the `url` and `credential` fields of the `secrets/shared/authentik-token` OpenBao
secret. Every consumer (`stacks/authentik`, `components/DockgeLxc.ts:774`'s outpost-token
minting, `stacks/applications/kubernetes.ts`) reads from that one place.

## 4. Cutover runbook

1. **Prerequisites closed:** §3.1 (fsync), §3.2 (backup + verified restore of a *scratch* alpha-site
   dump), §3.3 (break-glass paths fixed/confirmed), §3.4 (piece 03 landed).
2. **Deploy** the alpha-site authentik stack (server, worker, bundled Redis) pointed at a **fresh,
   empty** database via the shared Postgres instance. Confirm it starts healthy against an empty
   DB before touching real data.
3. **Cutover dump:** `pg_dump` authentik's database from SGC's CNPG primary → restore into the
   alpha-site Postgres via the shared instance. Verify row counts / a login round-trip before
   proceeding — this is the same "don't suspend mid-upgrade, watch for ownership drift on
   restore" caution the estate has hit before with `romm`/`windmill` restores.
4. **Repoint DNS/ingress** for `canterlot.driscoll.tech`, `iris.driscoll.tech`, and
   `authentik.driscoll.tech` (§1.4) from SGC's Traefik to alpha-site's Dockge Traefik.
5. **Repoint `AUTHENTIK_URL`/`AUTHENTIK_TOKEN`** in OpenBao (§3.5).
6. **Post-check:** every outpost re-registers and reports healthy against the new server
   (`authentik-remote-cluster` on both equestria and sgc, plus every Dockge-hosted proxy
   outpost); `forwardAuth`-gated apps still authenticate; a full login round-trip on at least one
   app per outpost type (embedded, proxy, Dockge-proxy).
7. **Soak.** No fixed duration specified here — align with whatever cadence
   [16 — soak and gate](16-soak-and-gate.md) establishes for the rest of the plan; authentik
   being wrong is worse than most things this plan touches, so err toward longer.
8. **Scale the SGC copy to zero.** Not delete — kept as the soft-rollback path (`kubectl scale
   deployment/authentik-server deployment/authentik-worker --replicas=0`, CNPG cluster left
   running or paused per its own guidance). Full teardown is
   [22 — decommission SGC](22-decommission-sgc.md)'s job, after the node phases complete.

## 5. What does not change

- **Outpost creation and registration mechanics** (§1.5) — the Dockge per-host outpost pattern
  and the cross-cluster `authentik-remote-cluster` chart are both already-proven, already-running
  infrastructure. This piece repoints what they talk to; it does not rebuild them.
- **Every app's own OIDC client configuration** — issuer URLs are the vanity aliases in §1.4,
  which don't change; only what answers behind them does.
- **`stacks/authentik`'s object management** (flows, groups, roles, providers) — it only needs a
  reachable `AUTHENTIK_URL`/`AUTHENTIK_TOKEN` (§3.5); it has no opinion on where the server runs.

## 6. Risks accepted

- **HA reduction: 2 server replicas → 1 box.** Authentik runs redundant server pods today; on
  alpha-site it becomes N, not N+1 — one Pi, one PSU, one USB cable. **Accepted.** Mitigation is
  not redundancy, it's a **rehearsed, verified restore** (§3.2) — the same posture the rest of
  this plan takes toward single points of failure elsewhere.
- **Concentration.** alpha-site now holds identity + the OpenBao seal + DR receiver + netboot.xyz
  + Gatus + AdGuard + Z-Wave + neo4j + Prometheus (§1.1). **Accepted, with the explicit rule that
  nothing else new lands here** — this piece's real deliverable includes that rule, not just the
  migration.
- **Rollback granularity is the dump interval, not continuous.** No PITR on the new instance
  regardless of how vault#119 resolves upstream (§1.3, §3.2).
