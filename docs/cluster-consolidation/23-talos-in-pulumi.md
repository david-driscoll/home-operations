# 23 — Talos machine config into Pulumi (Letter V)

> Follow-on, not critical path: machine config via `@pulumiverse/talos`,
> talhelper retired. Part of the
> [cluster consolidation plan](README.md) for
> [vault#84](https://github.com/david-driscoll/vault/issues/84); see that file
> for the decision ledger (D1–D12) and full sequencing graph. This file stands
> alone — no prior context required.

## What this delivers

The surviving cluster's Talos machine configuration, currently generated by
talhelper from `talos/talconfig.yaml` and applied by hand via
`.taskfiles/talos/Taskfile.yaml`, becomes a Pulumi resource tree using
[`@pulumiverse/talos`](https://www.pulumi.com/registry/packages/talos/) —
genuinely Pulumi-native machine config per **D10**, not Pulumi shelling out to
talhelper. talhelper is retired once parity is proven.

**This is explicitly not on the critical path.** Per **D10** and the issue's
own v2 §4 verdict: build the merge with today's known tools (talhelper +
talconfig), and bring the surviving cluster's machine config into Pulumi as a
follow-on afterward, proven by rebuilding one worker — not the other way
around. Putting an unproven, pre-1.0 provider in the path of the one cluster
that must not be put at risk was rejected explicitly during discovery.

## Depends on / sequencing

**Starts after [21](21-repo-consolidation-flux-repoint.md)'s exit gate** (the
merged cluster reconciles from `home-operations` alone) — same starting line
as [22](22-decommission-sgc.md), but independent of it. This piece does not
touch DNS, OpenBao, or repo archival, and 22 does not touch Talos machine
config. They can run in either order or in parallel.

## Verified starting state (2026-08-13)

- **No Talos tooling exists in Pulumi today.** `grep -rli "talos"
  components/ stacks/ --include="*.ts"` in `home-operations` returns
  nothing.
- **`@pulumiverse/talos` is not yet a dependency** — absent from
  `package-lock.json`. But **this repo already consumes pulumiverse
  packages**: `@pulumiverse/purrl ^0.6.2` (root `package.json`) and
  `@pulumiverse/unifi ^0.3.0` (`components/package.json`). Adding
  `@pulumiverse/talos` is not a new supply-chain decision, just another
  package from a publisher already trusted and pinned in this workspace.
- **talhelper is in active use today**, verified in `equestria-cluster`:
  - `.config/mise.toml` pins `talhelper = "3.1.16"` (and `talos = "1.13.8"`,
    `talosctl = "1.13.8"`, matching `versions.env`'s `TALOS_VERSION=v1.13.8`
    — today's version, ahead of the `v1.13.7` recorded in the original July
    discovery).
  - `.taskfiles/talos/Taskfile.yaml` drives it directly: `talhelper
    genconfig` (line 73), `talhelper gencommand apply --extra-flags
    '--mode={{.MODE}}' | bash` (line 106), `talhelper gencommand upgrade
    --extra-flags "--timeout=20m --wait" | bash` (line 136), plus per-node
    variants for `apply`/`bootstrap`/`upgrade`.
  - `talos/talconfig.yaml` is the source of truth: cluster name, endpoint,
    `additionalApiServerCertSans`, pod/service CIDRs, per-node hostname/IP/
    install-disk/machineSpec, and a `talos/patches/{global,controller,<node>}/*.yaml`
    tree (`machine-files.yaml`, `machine-registries.yaml`,
    `machine-sysctls.yaml`, `machine-kubelet.yaml`, `machine-network.yaml`,
    `machine-time.yaml`, plus controller-only `machine-rbac.yaml` and
    `cluster.yaml`, plus at least one node-specific patch,
    `un1290/machine-disks.yaml`). This patch tree is what
    `machine.getConfiguration({configPatches})` needs to reproduce
    faithfully — it is not a small surface.
  - Secrets: `talos/talsecret.sops.yaml` (sops-encrypted, not
    OpenBao/1Password) — this is the piece of the current toolchain that
    most directly needs replacing, since a Pulumi-native machine config
    wants its secrets in Pulumi config or OpenBao, not a third encryption
    scheme layered on top.
- **`netboot.xyz` is already running**, on alpha-site
  (`docker/alpha-site/netbootxyz`) — keep it. `@pulumiverse/talos` applies
  configuration to a node already booted into Talos maintenance mode; it
  does not PXE-boot bare metal or write install media.
- **`tuppr` is already running**, in-cluster
  (`kubernetes/apps/system-upgrade/tuppr`) — keep it for Talos/Kubernetes
  version upgrades. The provider has no upgrade resource; it owns
  configuration, not lifecycle.

## The retirement map

| talhelper does today | `@pulumiverse/talos` (0.8.0) replacement |
|---|---|
| `talconfig.yaml` + `talconfig.json` schema, `talhelper genconfig` | `machine.getConfiguration()`, called per node, assembled from Pulumi config/TypeScript rather than one big YAML |
| `talos/patches/**` (`configPatches` composition) | `machine.getConfiguration({ configPatches })` — same concept, now expressed as Pulumi inputs instead of a patch-file tree merged by talhelper |
| Schematic / system-extension generation (implicit via talhelper's image handling) | the `imageFactory` module — explicit resources for schematic generation |
| `talsecret.sops.yaml` (sops) | Pulumi config encryption, or OpenBao via the estate's existing `ref+openbao://` resolver (`components/store/refs.ts`) — consistent with how every other secret in this repo is sourced post-migration, rather than a fourth encryption scheme |
| `talhelper gencommand apply/bootstrap/upgrade \| bash` | `machine.ConfigurationApply`, `machine.Bootstrap` (upgrade stays with tuppr — see below) |
| — (talhelper has no equivalent) | `cluster.Kubeconfig` — a Pulumi-native kubeconfig output |

**What the provider deliberately does not replace, confirmed above:**
bare-metal PXE boot (`netboot.xyz`) and Talos/Kubernetes version upgrades
(`tuppr` + `talosctl`). Both stay exactly as they are.

## The rehearsal-target problem (D12 — needs David's confirmation)

The v2 discovery said "rehearse on alpha-site" — it was, at the time, the
documented non-production test target
(`CLAUDE.md:63`, still today: *"Test risky changes against a non-production
stack (alpha-site) first."*). That instruction is now **stale and
dangerous** for this specific piece, independent of whether it's stale for
anything else: alpha-site hosts authentik as of phase 07/08 (identity for
the whole estate), and it is a single Raspberry Pi 4 — rehearsing
create/destroy cycles of anything is a different risk profile on a box that
also has to answer every login on the estate.

**This is unresolved, and it is unresolved specifically because of an
ambiguous answer, not a missing one.** David's 2026-08-01 comment on the
test-target question read:

> *"alpha-site, assuming that it doesn't have any performance issues is the
> idea[l] machine. IDP needs to stay online more than any other service.
> Alpha site is a rasberry pi 4 that is poe powered, so it's downtime is
> dependent on the PoE switch it is getting powered by."*

That does not cleanly resolve to "yes, still rehearse there" or "no, move
the test target." It reads as much like an argument *against* using
alpha-site for anything risky (IDP needs to stay up more than anything
else) as it does an endorsement of alpha-site's suitability. The README's
decision ledger tracks this correctly as **D12: unconfirmed** — this piece
does not resolve it either, and should not proceed past rehearsal-target
selection without David picking one explicitly.

**Proposed alternatives, for confirmation before this piece executes:**

1. **A throwaway Proxmox VM on one of the estate's Proxmox hosts.** Cheapest
   to stand up and tear down repeatedly, fully isolated from anything
   production-facing, and matches how `hard-hat`/`shining-armor` (equestria's
   own Proxmox-VM control plane and worker) are already provisioned — so the
   rehearsal target is architecturally close to at least two of the real
   nodes it needs to prove config parity against.
2. **`skystar`** — measured during discovery at 4 cores, 4.47 GiB available,
   5.5% utilization, no estate-critical role. Already a candidate David's
   discovery comments floated for the general test-target re-designation
   question, independent of this piece.

Either works for this piece's narrow purpose (prove `@pulumiverse/talos` can
create and destroy a single-node Talos cluster unattended, twice). **Do not
default to alpha-site by inertia** — get an explicit answer, the same way
[08 — test-target re-designation](08-test-target-redesignation.md) needs one
for the estate generally. If David confirms alpha-site anyway despite the
IDP concentration, that's a valid answer too — the point is that it must be
asked, not assumed, given how the 2026-08-01 answer actually reads.

## Procedure

1. **Get the rehearsal-target question answered** (above) before writing any
   code against a real box.
2. Add `@pulumiverse/talos ^0.8.0` to the workspace (root `package.json` or
   `components/package.json`, matching where `@pulumiverse/purrl`/`@pulumiverse/unifi`
   already live).
3. Build the `client`/`cluster`/`imageFactory`/`machine` resource wiring for
   **one node's** configuration first, not the whole cluster — reproduce
   `talos/patches/global/*.yaml`'s six patch files as `configPatches` inputs,
   then the controller-only patches, then the one node-specific patch
   (`un1290/machine-disks.yaml`) to prove the per-node override path works
   too.
4. Wire secrets through Pulumi config or the `ref+openbao://` resolver — not
   a new sops file. This is the one piece of the current toolchain this
   migration should not carry forward unchanged, per the retirement map
   above.
5. **Rehearse on the confirmed target**: create a single-node Talos cluster
   from `home-operations` via the new Pulumi resources, destroy it, repeat —
   **twice, unattended** (no manual intervention between runs). This is the
   bar the discovery comments set and it should not be relaxed; a provider
   this new needs to prove it's boring before it touches anything real.
6. **Prove it for real: rebuild ONE worker from `home-operations`,
   unattended, twice.** Pick a worker (not a control plane — lower blast
   radius, matches the estate's own "VM before bare metal, worker before
   control plane" node-ordering convention used throughout the earlier
   phases) on the actual merged cluster. Wipe and reinstall it via the new
   Pulumi machine-config path twice in a row, unattended each time, and
   confirm it rejoins cleanly and Longhorn rebuilds fully both times before
   calling this piece done.
7. Only after step 6 succeeds twice: retire talhelper from `.config/mise.toml`
   and `.taskfiles/talos/Taskfile.yaml`, and delete `talos/talconfig.yaml` +
   `talsecret.sops.yaml` from the merged tree (they were already copied into
   `home-operations` unchanged by [21](21-repo-consolidation-flux-repoint.md);
   this piece is what actually replaces their function).

## Maturity caveat — stated plainly, not smoothed over

`@pulumiverse/talos` 0.8.0 is **pre-1.0 and community-maintained** (a bridge
over Sidero's `terraform-provider-talos`, not an official siderolabs
package). **Whether it tracks the Talos 1.13 machine-config schema without
gaps versus talhelper is unverified** — `versions.env` confirms the merged
cluster is on `TALOS_VERSION=v1.13.8` today, and the provider's schema
coverage against that specific version has not been checked against its
source in this session. The rehearsal in steps 5–6 is what answers this
question empirically; do not treat the provider's existence as proof it
covers everything talhelper does. If the rehearsal surfaces a config-patch
shape the provider can't express, that is a legitimate reason to stop and
keep talhelper for that node's config rather than force a fit.

## Exit gate

One worker, rebuilt from `home-operations` via `@pulumiverse/talos`
end-to-end (wipe → configure → apply → bootstrap-join → rejoin cluster →
Longhorn fully rebuilt), unattended, twice in a row, with no manual
intervention on either run. talhelper is removed from tooling and the repo
only after this gate passes — not before, and not conditionally.

## Risks and rollback

| Step | What breaks | How you'd know | Rollback | Point of no return |
|---|---|---|---|---|
| Rehearsal (step 5) | Provider produces a machine config the rehearsal target rejects, or one that boots wrong | Rehearsal cluster never comes up, or comes up misconfigured | Destroy the rehearsal target and retry — it's throwaway by design | None — this is the entire point of rehearsing somewhere disposable |
| Real worker rebuild (step 6) | The worker fails to rejoin, or a config-patch gap surfaces that talhelper's patch tree covered and the Pulumi wiring didn't | Node never `Ready`; Longhorn `degraded` on that node | Reinstall the node from the still-present talhelper/`talconfig.yaml` path — nothing in step 7 has happened yet, so the old tooling is still intact | None — this is exactly why step 7 (retiring talhelper) is gated on step 6 succeeding twice, not once |
| Talos version drift | Provider was rehearsed against `v1.13.8`; a later Talos upgrade (via tuppr) moves past what the provider's schema tracking covers | Next machine-config change via Pulumi fails or silently drops a field | Fall back to hand-editing via `talosctl patch` for that one change, re-verify provider coverage before trusting it again | None — this is a standing maintenance cost of a pre-1.0 provider, not a one-time risk |
| Rehearsal-target ambiguity (D12) | Building against an assumed target (e.g. defaulting to alpha-site) that David didn't actually confirm | Discovered after the fact, possibly after alpha-site has already taken rehearsal load | Re-run the rehearsal on the confirmed target once D12 is answered | None, but it wastes the rehearsal and risks alpha-site load during the IDP-hosting window unnecessarily |
